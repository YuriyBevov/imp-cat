# Техническое задание ICAT Document Translation Studio

Статус: актуальное, источник истины для дальнейшей разработки  
Версия: 1.2
Дата: 5 сентября 2026 года
Рабочая ветка: `experiment/codex-document-agent`

## 1. Назначение продукта

ICAT — внутреннее приложение бюро переводов для полного цикла работы с документом:

1. загрузка PDF или изображения;
2. извлечение всего видимого текста и структуры документа;
3. разбиение содержимого на редактируемые логические сегменты;
4. перевод с учётом базы утверждённых переводов и терминологии;
5. визуальная корректировка расположения и типографики;
6. автоматическая проверка текста и макета;
7. выгрузка редактируемого DOCX и фиксированного PDF.

Цель — подготовить технически полноценную переводную версию документа. Пиксельное копирование исходника не требуется, но должны сохраняться страницы, порядок чтения, логическая структура, взаимное расположение элементов и назначение специальных областей.

## 2. Принятые архитектурные решения

- Основным источником текста, сегментации и классификации является один мультимодальный агент.
- В интерфейсе выбирается единый AI-маршрут: Codex CLI с авторизацией ChatGPT либо AITunnel API. Выбор применяется к первичному анализу, повторному анализу и переводу.
- Приложение не извлекает текст локально перед агентом: выбранная мультимодальная модель получает изображения страниц и является единственным источником текста и структуры.
- Локальные инструменты отвечают за безопасное хранение файла, рендер страниц, нормализацию координат, интерфейс, валидацию и экспорт.
- RapidOCR и ONNX удалены из текущей ветки и сохраняются только в архивной ветке `experiment/client-requirements-v2`.
- Агент возвращает данные только по строгой JSON Schema. DOCX/PDF собираются детерминированным кодом, а не генерируются моделью.
- Все координаты агента нормализованы относительно исходной страницы в диапазоне от `0` до `1`.
- Исходный текст никогда не перезаписывается переводом.

## 3. Поддерживаемые форматы

### Вход первой версии

- PDF, включая сканированные многостраничные документы;
- PNG;
- JPEG/JPG;
- WebP;
- TIFF;
- HEIC;
- BMP.

### Выход первой версии

- DOCX — редактируемый документ;
- PDF — фиксированное представление утверждённой сцены.

DOCX как входной формат относится к следующему этапу. Для сохранения визуальных объектов такой файл необходимо предварительно преобразовывать в PDF.

## 4. Основной пользовательский сценарий

1. Пользователь одновременно выбирает один или несколько документов.
2. Для каждого файла создаются независимое фоновое задание и вкладка с прогрессом.
3. Сервер сохраняет оригинал и локально создаёт PNG каждой страницы без извлечения текста.
4. Выбранный мультимодальный агент получает все страницы одного документа и строгую инструкцию анализа.
5. Агент извлекает полный текст, определяет логические сегменты, порядок чтения, координаты, типы объектов и базовые стили.
6. Сервер проверяет ответ по JSON Schema и внутренним ограничениям.
7. Из результата создаётся `DocumentScene`, после чего готовая вкладка открывается в редакторе ICAT.
8. Пользователь сверяет сегменты с оригиналом; в колоночном режиме исходник находится слева, перевод — справа.
9. Каждый внешний сегмент при необходимости делится на внутренние переводческие единицы без изменения координат страницы.
10. Для каждой единицы ICAT сначала предлагает 100% совпадение из БЗ, а при его отсутствии запрашивает перевод у выбранной AI-модели.
11. Пользователь подтверждает переводы и явно добавляет новые пары в БЗ.
12. После первичной верстки агент сравнивает оригинальные страницы с рендером рабочей сцены и предлагает структурированные команды исправления.
13. Пользователь подтверждает или отклоняет рекомендации.
14. Сервер валидирует сцену и собирает DOCX/PDF.

## 5. Результат первичного анализа агента

Для каждой страницы агент обязан вернуть:

- индекс страницы;
- язык или набор языков;
- полный перечень видимых объектов;
- порядок чтения;
- логическую группу потока;
- нормализованные координаты;
- типографику;
- уверенность;
- признак обязательной ручной проверки.

Поддерживаемые типы объектов:

- `text` — обычный текст, заголовок или абзац;
- `table` — таблица целиком, если структура не может быть безопасно разделена;
- `table_cell` — отдельная ячейка таблицы;
- `stamp` — штамп;
- `seal` — печать, включая круглую;
- `signature` — подпись;
- `handwriting` — другая рукописная запись;
- `logo` — логотип;
- `image` — значимое изображение;
- `unknown` — видимый, но не классифицированный объект.

## 6. Специальные объекты

Печати, штампы, подписи и логотипы нельзя удалять или заменять только пустым маркером.

Для такого объекта сохраняются:

- тип и русская подпись типа;
- весь уверенно читаемый текст;
- оригинальная область страницы;
- координаты;
- уверенность;
- комментарий о неразборчивых частях.

Отображение в редакторе и переводе:

```text
[Штамп]
MERSİN 3. NOTERLİĞİ
25 Ağustos 2023
No: 18871
```

Если текст отсутствует или не читается, агент возвращает пустой `sourceText` и пояснение `Текст неразборчив`. Агент не должен угадывать рукописный текст.

## 7. Правила сегментации

- Каждый сегмент должен быть логически редактируемой единицей: заголовком, абзацем, подписью, штампом, ячейкой или самостоятельной строкой реквизитов.
- Нельзя объединять независимые колонки, таблицу с основным текстом или подпись с соседним абзацем.
- Нельзя терять короткие подписи, номера, даты, колонтитулы и текст внутри печатей/штампов.
- Один сегмент может иметь несколько `regions`, если его строки визуально разделены.
- Для каждого сегмента задаётся устойчивый ID, `pageIndex`, `readingOrder` и `flowGroup`.
- Сегменты создаются до перевода; перевод не меняет исходную сегментацию автоматически.
- Геометрический сегмент страницы и переводческая единица — разные уровни модели. Абзац можно разбить на предложения или выделенный фрагмент внутри `translationUnits`, не создавая новые координатные блоки.

## 8. Модель рабочей сцены

`DocumentScene` хранит отдельно:

- оригинальные размеры страниц;
- изображения страниц;
- исходные и текущие координаты;
- исходный текст;
- перевод;
- внутренние переводческие единицы: исходник, перевод, разделитель, статус, предложение БЗ и ID утверждённой записи;
- тип объекта;
- стили;
- логический поток;
- историю ручных изменений;
- статус проверки;
- происхождение данных и модель агента.

Ручной зум влияет только на отображение и не изменяет документные координаты.

## 9. Перевод и база знаний

- В интерфейсе выбирается единый провайдер AI: AITunnel либо Codex; смешанный скрытый маршрут не допускается.
- Каталог моделей AITunnel загружается динамически. Для полного маршрута выбирается модель с поддержкой изображений и текстового ответа.
- Подключение проверяется через авторизованный каталог моделей без платной генерации.
- Ключ AITunnel передаётся из браузера backend в RSA-OAEP-шифротексте. По явной опции он сохраняется в серверном `.env`, исключённом из Git и доступном только владельцу серверного процесса.
- Backend обращается к AITunnel только через HTTPS. В production сам интерфейс ICAT также обязан обслуживаться через HTTPS.
- Сначала для каждой внутренней единицы ищется 100% совпадение в базе утверждённых переводов.
- Точное совпадение показывается как предложение и не применяется без действия пользователя.
- Если точного совпадения нет, единица передаётся выбранной AI-модели. Вторая скрытая модель или локальный переводчик не подключаются.
- Поиск похожих записей выполняется отдельным векторным индексом и используется только как ручная подсказка, а не как автоматическая подстановка.
- Внешняя геометрия сегмента при внутреннем разбиении не меняется; итоговый перевод собирается из единиц только после заполнения всех частей.
- Все машинные переводы требуют подтверждения переводчиком.
- Подтверждённая пара добавляется в БЗ только по явной команде пользователя. Если точный исходник для целевого языка уже существует, дубликат не создаётся и существующая запись не перезаписывается молча.
- Текущий прототип хранит записи и локальные хеш-векторы атомарно в JSON. Контракт API отделён от хранилища, чтобы в production заменить файл на PostgreSQL/pgvector и модельные embeddings без изменения редактора.

## 10. Автоматическая проверка макета

После первичной сборки сервер рендерит редактируемые страницы в изображения. Агент сравнивает их с оригиналом и возвращает только команды:

- перемещение;
- изменение размеров;
- изменение размера шрифта и межстрочного интервала;
- изменение выравнивания;
- перенос на другую страницу;
- изменение порядка;
- отметка пропуска, дубликата или пересечения.

Команды не применяются без подтверждения пользователя. Все применения входят в undo/redo.

## 11. Экспорт

- PDF строится из утверждённой координатной сцены.
- DOCX строится из секций, абзацев, таблиц и позиционируемых объектов.
- Исключённые и находящиеся вне документа сегменты не экспортируются.
- Перед скачиванием проверяются ZIP-контейнер DOCX, XML, ссылки, идентификаторы объектов и количество страниц.
- Там, где это возможно, DOCX дополнительно открывается LibreOffice в headless-режиме для smoke-проверки.

## 12. Адаптеры агента

Codex запускается сервером как доверенный локальный процесс:

- авторизация — сохранённая сессия `codex login` через ChatGPT;
- модель по умолчанию — `gpt-5.6-sol`;
- вход — PNG страниц текущего пакета;
- выход — JSON по схеме `schemas/document-analysis.schema.json`;
- режим — `--ephemeral`, без сохранения агентного диалога;
- песочница — `read-only`;
- максимальное время обработки на документ настраивается;
- stdout/stderr не передаются в браузер целиком и не должны содержать секреты.

Это облачный вызов OpenAI через авторизацию ChatGPT, а не локальная модель. Адаптер AITunnel использует тот же контракт анализа, отправляет PNG через OpenAI-совместимый `chat/completions` и принимает структурированный JSON. Редактор и экспорт не зависят от выбранного адаптера.

## 13. Ошибки и восстановление

- При недоступном выбранном агенте загрузка завершается понятной ошибкой; другой механизм распознавания не включается молча.
- Оригинал и изображения страниц сохраняются, чтобы повторить анализ без повторной загрузки.
- Невалидный ответ агента не преобразуется в частичную сцену.
- Повторный запуск создаёт новую ревизию анализа и сохраняет предыдущий результат для диагностики.
- Ответ AITunnel сохраняется локально без ключа и HTTP-заголовков; при ошибке показываются `finish_reason`, размер ответа и причина обрыва.
- Статус `failed` является терминальным: браузер прекращает polling и явно показывает остановку обработки.
- Длинные документы обрабатываются последовательными пакетами той же моделью; каждая страница анализируется один раз, а базовый размер пакета равен двум страницам.
- Лимит выхода не рассчитывается по страницам и не обрезается ICAT: AITunnel получает точный `max_output` из каталога выбранной модели; при отсутствии значения парамет лимита не отправляется.
- После каждого пакета сохраняется локальная контрольная точка; при ошибке следующие API-запросы не запускаются.
- До перехода в production анализ должен выполняться как фоновое задание с ID и опросом статуса: контрольный четырёхстраничный Arbel занял 13 минут 53 секунды, поэтому один открытый HTTP-запрос допустим только для локального прототипа.

## 14. Безопасность и конфиденциальность

- Документы находятся в локальном хранилище ICAT, но при агентном анализе изображения отправляются выбранному провайдеру: OpenAI через Codex либо AITunnel по HTTPS.
- В интерфейсе должно быть явно указано, какой агент обрабатывает документ.
- Нельзя писать содержимое документов или токены авторизации в серверный лог.
- Codex запускается с минимальными правами и получает только каталог конкретного задания.
- Результаты и исходники должны удаляться согласно политике хранения бюро.
- Секретный ключ AITunnel не возвращается браузеру, не пишется в логи, сцену, диагностические файлы или Git. API возвращает только признаки наличия и способа хранения.
- Серверный `.env` создаётся атомарно с правами `0600`, не может быть симлинком и исключён из Git. Секрет внутри `.env` не зашифрован, поэтому доступ к файлу должен быть ограничен на уровне серва.

## 15. Критерии приёмки базового этапа

На контрольных документах Arbel и UNH:

- извлечён весь читаемый текст без заметных пропусков;
- страницы и порядок чтения совпадают с оригиналом;
- печати, штампы и подписи классифицированы и содержат читаемый текст;
- каждый объект находится внутри правильной страницы;
- сегменты открываются в текущем редакторе;
- исходный текст можно исправить, перевести и сохранить;
- DOCX и PDF успешно создаются и открываются;
- полный набор автоматических тестов проходит;
- длительный анализ не удерживает открытым исходный HTTP-запрос, а прогресс доступен по ID задания;
- можно загрузить несколько документов и переключаться между обрабатываемыми/готовыми вкладками;
- завершённые локальные документы возвращаются во вкладки после перезагрузки интерфейса;
- режим «Сегменты» показывает для каждого объекта отдельные колонки исходника и перевода;
- документ на 30 и более страниц обрабатывается пакетно в рамках одного фонового задания;
- архивный документ не показывается в рабочих вкладках, но может быть восстановлен;
- окончательное удаление документа требует явного подтверждения;
- AITunnel/Codex переключаются в интерфейсе без раскрытия ключа, а весь AI-трафик следует выбранному маршруту;
- текстовые модели без Vision нельзя выбрать для полного документного маршрута;
- прежний локальный OCR-режим отсутствует в текущей ветке и доступен только в архивной ветке Git.
- 100% совпадение БЗ предлагается отдельно, а сегменты без точного совпадения переводятся выбранной AI-моделью;
- абзац разбивается на внутренние переводческие единицы без потери координат внешнего сегмента;
- подтверждённые единицы добавляются в БЗ без создания точных дубликатов.
